# Tokenization 深读：BPE 的算法、变体与那些怪现象

这篇是 **Tokenization 分词**主题的深度补充。分词是大模型管线里最不起眼却影响最深远的一环——「LLM 数学差」「数不清 strawberry 里有几个 r」「中文更贵」这些现象的根源都在 tokenizer。这里讲清 **BPE 的训练与编码算法**、**三大变体的差异**，以及**词表大小怎么权衡**。

> [!KEY] 一句话抓住本质
> BPE 从**单字符**词表出发，**反复合并语料里出现最多的相邻对**，直到词表达到预算——高频组合（如 "tion"、"的"）逐步长成独立 token。它天然在「字符太多」与「整词太少」之间爬到中间点：常见词整块表示（序列短），生僻词拆开表示（永不 OOV）。

---

## 一、BPE 训练：合并最频繁的邻居

```
初始词表 = 所有单字符（含 byte 级：256 个）
重复直到词表满：
    统计所有相邻 token 对的出现次数
    把最高频对 (A, B) 合并成新 token AB，加入词表
    语料中所有相邻的 A B 替换为 AB
```

例子（词频：low×5, lower×2, newest×6, widest×3）：

| 轮 | 最高频对 | 合并后 |
|---|---|---|
| 1 | (e,s) 出现 9 次 | 新 token `es` |
| 2 | (es,t) 8 次 | `est` |
| 3 | (est,`</w>`) 8 次 | `est</w>` |
| 4 | (l,o) 7 次 | `lo` … |

**编码**（推理时）：对新文本，按训练时学到的合并规则**按序应用**（存成 ranked merges 表）——同样的贪心顺序保证训练/推理一致。

> [!NOTE] Byte-level BPE（GPT 系）
> 直接在**字节**上跑 BPE：任何 UTF-8 字符串都是字节序列——**数学上杜绝 OOV**，任何语言/emoji/代码共用一套 256 起步的字母表。代价：生僻内容会退化成多字节 token（一个中文生僻字 3+ token）。

## 二、三大变体对照

| | BPE | WordPiece（BERT） | SentencePiece（T5/Llama） |
|---|---|---|---|
| 合并判据 | 频次最高 | **似然增益**最高（`##` 标续接） | BPE/Unigram 两种内核 |
| 粒度 | byte/char | char | **语言无关**（直接吃原始文本，不需要预分词） |
| 代表 | GPT-2/4, Claude | BERT | Llama, T5, Qwen, DeepSeek |
| 空格处理 | 词首 Ġ 标记 | 词内 ## | 把空格当普通符号（▁） |

**Unigram（SentencePiece 的另一内核）**：从大候选集出发，假设每 token 独立概率，用 EM 拟合，再**剪掉对似然贡献最小的 token**——与 BPE 的「自底向上合并」相反，是「自顶向下剪枝」，对多语言更均衡。

**中文的处境**：byte-level BPE 下一个常用汉字通常是 1 token（词表里学到了），但**同样语义的中文比英文多耗 1.5~2 倍 token**（信息密度/词表分配原因）——这是 API 按 token 计费时中文用户多付的钱。

## 三、词表大小与「tokenizer 病」

**词表权衡**：词表大 → 常见序列更短（推理快、上下文利用率高），但 embedding 参数线性膨胀（V×d）且低频 token 学不好；词表小 → 序列长、计算贵。现代主流 3 万~15 万：GPT-2 5 万、LLaMA 3.2 万、Qwen 15 万+（中文优化）。

**由 tokenizer 引发的著名怪象**：

1. **数学/计数差**：`1234` 可能被切成 `12|34` 或 `123|4`——模型「看」不到数位结构；「strawberry 有几个 r」同理。解法：一位数字一个 token 的专用词表，或干脆在推理时写代码。
2. **反向拼写困难**：token 是正向合并的产物，拆解（反向）不在自然操作里。
3. **敏感词绕过**：换个编码（全角/插入符）就能把一个 token 打散成训练分布外的组合——安全过滤若在 token 级做，就被 tokenizer「戏法」绕过。
4. **首 token 延迟与费用**：一切按 token 计价，分词边界直接影响成本与上下文窗口的可用容量。

## 常见误区

- **「tokenizer 是无损的（encode→decode = 原文）」** —— BPE/WordPiece 对大多数文本是无损的，但空格处理、Unicode 归一化、特殊 token 插入可能导致**微妙的不可逆变化**——LLM 的 prompt 对「不可见字符」敏感的原因。
- **「词表越大 = 模型越强」** —— 词表大小是压缩率与参数量的权衡：大词表减少序列长度（省钱）但增加 embedding 参数——最优词表取决于语料语言分布与训练预算。
- **「token 数量 = 字符数 / 4（英文经验公式对中文也适用）」** —— 中文/日文/韩文的 token 效率低于英文（同语义更多 token）——多语言模型的 token 计费差异是实际成本考量。
- **「改变 tokenizer 只影响输入格式不影响模型能力」** —— tokenizer 决定了模型的「感知粒度」：不同分词导致不同的推理难度（数字逐位分词利于算术、子词分词利于形态学）——tokenizer 是模型能力的一部分。

## 四、要点总结

1. **BPE 的训练过程？** 单字符起步，反复合并最高频相邻对直到词表预算；编码时按同样的合并次序贪心应用。
2. **BPE 与 WordPiece 的区别？** 合并判据：频次 vs 似然增益（$\frac{P(AB)}{P(A)P(B)}$ 高者优先）；WordPiece 用 ## 标记词内续接。
3. **byte-level 的意义？** 以 256 字节为底，任何文本可编码——OOV 数学上不可能。
4. **SentencePiece 解决什么？** 语言无关：不需预分词/空格假设，中日文等无空格语言与英文同一管线；支持 Unigram 内核。
5. **为什么 LLM 数不准字母数？** 词内结构被合并成一个 token，模型看不到字符级组成；需要时显式分字符或用代码。
6. **词表大小怎么选？** 序列长度与 embedding 参数的权衡；多语言场景为高频语言多分配 token（Qwen 路线）。
