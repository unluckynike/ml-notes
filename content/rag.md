# RAG 深读：从朴素检索到生产系统

这篇是 **RAG 检索增强生成**主题的深度补充。RAG 是 LLM 落地最广的工程范式，但「文档切块 → 向量检索 → 拼 prompt」只是及格线。这篇按一条真实的迭代路径讲：**朴素 RAG 会死在哪，每个环节的进阶手段是什么，怎么评估**。

> [!KEY] 一句话抓住本质
> RAG 把「参数化记忆」（模型权重，贵、静态、会幻觉）换成/补上「非参数化记忆」（外部库，便宜、实时、可溯源）。生成模型的职责从「记住知识」降级为「**用好检索到的上下文**」——所以 RAG 系统的上限通常由**检索质量**决定，而不是生成模型。

---

## 一、为什么要外挂知识

微调注入知识的三个硬伤：训练成本高、更新延迟大（每次新文档都要重训）、来源不可溯源。RAG 反过来：

| 维度 | 微调 | RAG |
|---|---|---|
| 知识更新 | 重新训练/微调 | 重建索引（分钟级） |
| 可溯源 | 否（藏在权重里） | **是**（引用到段落） |
| 幻觉控制 | 弱 | 强（有据可依） |
| 改变行为/风格 | 强 | 弱 |

经典结论（与 LoRA 深读互相印证）：**知识 → RAG，行为 → 微调**，两者不冲突。

---

## 二、朴素 RAG 流水线与它的死法

```
文档 → 切块(chunk) → 嵌入(embed) → 向量库 →
查询 → 嵌入 → top-k 检索 → 拼进 prompt → 生成
```

朴素版在各环节的典型死法：

| 环节 | 症状 | 根因 |
|---|---|---|
| 切块 | 答案被拦腰截断 | 固定长度切块切断语义单元 |
| 嵌入 | 换个问法就检索不到 | 查询与文档的「词汇鸿沟」 |
| 检索 | top-k 里没有答案段 | 单路检索盲区；k 太小漏 / 太大噪 |
| 生成 | 上下文里有答案还说错 | 上下文太长中间被忽略（lost in the middle）；指令弱 |

下面逐环节给进阶手段。

---

## 三、切块：语义单元优先

- **大小经验值**：256~1024 token，问题粒度越细块越小（FAQ 类小块，报告类大块）。
- **重叠滑窗**（10~20%）防边界截断。
- **按结构切**：Markdown 标题 / HTML 标签 / 代码函数边界优先于定长——语义完整性 > 尺寸规整。
- **小块检索 + 大块生成（small-to-big / sentence-window）**：用小段做精确匹配定位，喂给生成模型的却是其所属大段——**检索精度与上下文完整性兼得**，这是生产系统最常见的升级。
- **父子块 / 上下文扩展**：向量库（如 LanceDB/LlamaIndex）原生支持「命中小块、取父节点」。

---

## 四、检索：单路必死，混合当立

### 4.1 稠密检索的盲区

向量嵌入擅长**语义**（「怎么退货」≈「退款流程」），但对**精确 token** 弱：型号「A320neo」、报错码「ERR_CONN_1042」可能被嵌入空间抹平。

### 4.2 混合检索（hybrid）

BM25（稀疏，词面精确匹配）+ 稠密向量，用 **RRF（reciprocal rank fusion）** 融合：

$$\text{score}(d) = \sum_{i \in \text{retrievers}}\frac{1}{k + \text{rank}_i(d)}$$

$k$ 常取 60。RRF 只用排名不用分数，天然规避两路分数量纲不可比的问题。生产 RAG 的默认形态。

### 4.3 向量库与 ANN

精确最近邻是 $O(n)$ 暴力扫描，大规模库用近似索引：**HNSW**（跳表式近邻图，高召回低延迟、内存大）是主流；IVF/PQ 族省内存但有训练步骤。选型要点：库规模、过滤条件（metadata filter 是否下推到索引层）、更新频率。

### 4.4 查询侧改造

- **查询改写**：让 LLM 把口语问题重写成检索友好形式（补全指代、拆分多问）。
- **HyDE**：先让 LLM **假设性地写一段答案**，拿这段假答案去检索——答案与文档同分布，比「问题 vs 文档」的鸿沟小。
- **多查询扩展**：一个查询改写成 N 个变体分别检索再融合（以延迟换召回）。

---

## 五、重排：便宜又大涨点的一环

初检（召回）用双塔/向量快而糙；**重排**用交叉编码器（cross-encoder）慢而准——query 和文档拼在一起过模型，逐对打分，交互注意力能捕捉双塔各自编码丢失的细粒度匹配：

| | 双塔（bi-encoder） | 交叉编码器（cross-encoder） |
|---|---|---|
| 结构 | query、doc 各自编码，cosine 打分 | 拼接后联合编码打分 |
| 速度 | 快（doc 可离线编码） | 慢（每对都要前向） |
| 角色 | 召回 top-50~100 | 精排 top-3~8 |

> [!TIP] 投入产出比最高的单点优化
> 在朴素 RAG 上加一个 reranker（bge-reranker / Cohere Rerank），常见指标（答案命中率）提升立竿见影，改动成本极小。实战中值得优先做这一环。

---

## 六、生成：抗「lost in the middle」与引用

- 检索段**按重排分数排序**再拼 prompt；关键段放开头/结尾（中间位置注意力最弱）。
- 指令明确：「仅依据以下资料回答；资料不足就明说」——把「拒答」变成合法输出是压幻觉的第一道闸。
- **引用机制**：要求每句话标注来源块编号，后处理校验引用存在性；用户信任与调试都依赖它。
- 上下文预算：留足生成空间，超长时宁可少拼几段（精排后的头部），也别全塞。

---

## 七、评估：没有指标就没有迭代

两级评估（缺一不可）：

**检索级**：context recall（该召回的召回了没）、context precision（召回的里有用率）、MRR/NDCG。可用合成问题（从文档生成 QA 对）自动做。

**生成级**：faithfulness（答案是否忠于检索内容，可让强 LLM 抽取答案主张再逐条对上下文验证）、answer relevance、正确性比对 ground truth。工具链：RAGAS / TruLens / LlamaIndex evaluators。

> [!NOTE] 分级定位故障
> 答案错 → 先看检索对不对（context recall）→ 检索对但答错才是生成问题（加 rerank/改 prompt）→ 检索不对是切块/嵌入/查询改写问题。**别上来就换大模型。**

---

## 八、进阶形态一览

- **迭代式 RAG（Self-RAG / CRAG）**：模型自己判断「检索够不够、答案有没有依据」，不够就重检索/改写再来一轮。
- **GraphRAG**：先抽实体关系建知识图谱，检索沿图扩展——应对「全局性总结」类问题（朴素 RAG 只会捞局部段落，答不了「这批文档的主要主题」）。
- **Agentic RAG**：检索变成 Agent 的工具，多步规划（拆问题→多源检索→汇总），代价是延迟与不确定性。
- **多模态 RAG**：图表截图用 VLM 描述或 ColPali 式视觉嵌入入库——PDF 里一半信息在图里，纯文本管线看不见它们。

## 九、要点总结

1. **RAG 与微调怎么选？** 知识注入/实时更新/可溯源 → RAG；行为风格/领域语感 → 微调；常组合使用。
2. **为什么需要混合检索？** 稠密擅长语义泛化、弱在精确词面；BM25 相反；RRF 融合两者排名。
3. **reranker 为什么能提升？** 交叉编码逐对交互，捕捉双塔「各自编码再 cosine」丢失的细粒度信号；慢所以只精排头部。
4. **切块的原则？** 语义单元完整性优先；small-to-big 解耦「检索粒度」与「生成上下文粒度」。
5. **RAG 怎么评估？** 检索级（recall/precision）+ 生成级（faithfulness/relevance）双层，先定位层级再优化。
6. **lost in the middle 是什么？** 长上下文里中间位置的信息利用率显著低于首尾；对策是重排排序、限制段数、关键信息放两端。
