# Agent 深读：ReAct 循环、工具调用与记忆设计

这篇是**Agent 与工具调用**主题的深度补充。2023 年前「让 LLM 自主调用工具完成任务」是论文；现在它是产品标配。这篇把 Agent 拆成**一个循环 + 三个模块**（工具、记忆、规划），讲清工程上真正决定成败的设计点。

> [!KEY] 一句话抓住本质
> Agent = LLM 进入「**感知 → 思考 → 行动 → 观察**」的循环：模型输出的不只是文本，还有**结构化的行动指令**（调哪个工具、什么参数），执行结果拼回上下文再进入下一轮，直到任务完成。ReAct 论文给的这个循环至今没变，变的只是每个模块的成熟度。

---

## 一、ReAct：推理与行动交织

ReAct（Yao et al., 2022）的提示模板只有一个格式约定：

```
Thought: 我需要先查一下今天上海的天气
Action: search[上海 今日天气]
Observation: 多云，18~24°C，降水概率 10%
Thought: 天气不错，适合户外，可以推荐去外滩
Action: finish[建议：外滩散步，气温舒适无需带伞]
```

两个关键收益：

1. **思考可见**：Thought 强迫模型外化中间推理，出错可审计、可干预；
2. **行动落地**：模型不用「背」事实，检索/计算交给工具（事实性大幅提升，与 RAG 同理）。

现代 function calling 是同一范式的结构化版：模型输出 JSON（`{"name": "get_weather", "arguments": {...}}`），由运行时执行——格式约束从「提示词求它」变成「受约束解码保证」，可靠性天差地别。

## 二、工具：接口设计的工匠活

工具定义 = 给模型看的「API 说明书」，质量直接决定调用成功率：

- **描述写给模型而非人**：说清什么时候用、什么时候别用、参数含义与单位；一个反例：「query: 字符串」——模型只能猜。
- **数量与粒度**：工具太多（>20）选择准确率下降——按任务分组/路由；粒度太细会触发「调用地狱」（十次小调用不如一次大调用）。
- **返回值要「模型友好」**：截断的关键结果比全量 dump 好；错误信息要可行动（「city 不存在，可用值：…」而不是 stack trace）。
- **MCP（Model Context Protocol）**：把「工具/资源/提示」标准化成统一协议——工具生态从「每家私有插件」走向「即插即用」，是 2024 年后 Agent 工程的基础设施。

## 三、记忆：两个时间尺度

**短期记忆 = 上下文窗口**：一切都在这里，受长度与成本约束。管理手段：压缩（把旧轮次摘要成短文本）、淘汰（滑动窗口+锚定摘要）、结构化（把「待办/已知事实」抽成清单放系统提示）。

**长期记忆 = 外部存储**：向量库（语义检索过往经验）、KV 缓存复用（前缀缓存省钱提速）、文件式记忆（MemGPT/Letta 思路：让 Agent 自己决定什么写进长期存储、何时读回）。设计要点：**写什么、何时读、怎么遗忘**——与人类记忆一样，全记等于没记。

> [!TIP] 经验法则
> 短期记忆解决「这轮任务连贯」，长期记忆解决「跨会话像同一个人」。多数产品级 Agent 失败在长期记忆的检索质量（等价于一个 RAG 子问题），而不是「智商」。

## 四、规划与控制流

| 模式 | 流程 | 适用 |
|---|---|---|
| **ReAct 单环** | 边想边做 | 简单任务、探索型 |
| **Plan-and-Execute** | 先列计划再逐步执行 | 步骤多、需要全局观 |
| **反思（Reflexion）** | 失败后生成「下次教训」存入记忆 | 易错任务、可重试 |
| **多 Agent 编排** | 见「多智能体协作」深读 | 角色分工/并行 |

**控制权设计**：循环要有终止条件（最大步数、超时、成本上限）与人工检查点（高风险动作前暂停确认）——**自主性与可控性是 Agent 的第一对矛盾**，产品上永远默认「可中断、可回滚、可审计」。

## 五、评估：Agent 怎么打分

- **端到端任务成功率**（对真实环境的确定性评测集，如 SWE-bench、WebArena）——唯一硬通货；
- **轨迹质量**：步数、工具选择正确率、恢复能力（注入错误后能否自救）；
- **成本与延迟**：每任务 token 消耗是产品生死线（反思型 Agent 常比单环贵 5~10 倍）。

常见失败画像：工具选择错（描述不清）、参数幻觉（给不存在的城市）、循环不终止（缺停止条件）、把工具输出当指令（prompt injection——工具返回内容必须当数据不当指令，见安全要点）。

## 常见误区

- **「Agent = LLM + 更多工具」** —— 工具多不等于能力强。没有清晰的任务分解与错误恢复机制，更多工具只会增加选择混乱与失败面。核心是循环设计（计划/执行/观察/修正），不是工具清单长度。
- **「ReAct 循环一定会收敛到答案」** —— 不会。缺少终止条件与最大步数限制，Agent 可能陷入「搜索-失败-再搜索」的死循环；工程上必须有预算硬约束。
- **「给了工具描述模型就会用」** —— 工具描述的质量直接决定调用准确率；模糊的描述 = 随机调用。工具设计是 Agent 工程中被低估的核心技能。
- **「多步推理的任务一定需要 Agent」** —— 如果步骤可预知且固定，一个精心设计的 prompt + 确定性代码比 Agent 更可靠更便宜。Agent 的价值在「步骤不可预知」的场景。

## 六、要点总结

1. **ReAct 的核心贡献？** 把「推理 Trace」与「行动」放进同一循环，模型边想边调工具边观察——现代 Agent 的最小完整形态。
2. **function calling 为什么比让模型输出命令文本可靠？** 结构化输出走受约束解码，JSON schema 保证格式合法；文本解析再稳也有漏网率。
3. **工具设计三原则？** 描述面向模型（何时用/不用）、数量克制（分组路由）、返回值可行动（错误给建议）。
4. **短期 vs 长期记忆？** 上下文窗口（压缩/淘汰/结构化）vs 外部存储（向量检索/自管理文件）；长期记忆检索本质是 RAG 子问题。
5. **Agent 评估看什么？** 真实环境任务成功率第一；轨迹效率与成本是工程约束。
6. **prompt injection 在 Agent 里为什么危险？** 工具返回的内容可能含恶意指令且直接进入上下文；防御：内容当数据、来源标记、敏感动作需人确认。
