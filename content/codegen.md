# 代码生成深读：约束解码的编译链与执行反馈

这篇是**代码生成与结构化解码**主题的深度补充。演示里的「掩码随状态收紧」是受约束解码的末端，它的完整链路是**文法 → 状态机（FSM）→ 每步 logits 掩码**。这篇讲清这条编译链，以及代码生成的另一个支柱——执行反馈循环。

> [!KEY] 一句话抓住本质
> 受约束解码把「格式正确」从概率问题变成数学保证：**文法编译成有限状态机，每个解码步只允许状态机的转移边对应的 token**。语义正确性它管不了——那由执行反馈（跑测试→修错）负责。两层正交，缺一不可。

---

## 一、编译链：文法 → FSM → 掩码

以 JSON 为例：

1. **文法**：JSON Schema 或 GBNF（llama.cpp 的文法格式）描述「什么样的字符串是合法的」；
2. **编译**：把文法转成 FSM——每个状态记录「下一步接受哪些 token」；实现上对词表每个 token 检查「它是否能从当前状态开始合法续写」（Outlines 用正则→FSM 的经典编译，token 级做前缀缓存）；
3. **解码**：每步取当前状态的合法 token 集，logits 里非法项置 −∞，softmax 重归一后采样；采样后状态机转移。

三个工程细节：

- **词表对齐**：一个 token 可能横跨多个文法状态（如 `": "` 整个是一个 token）——FSM 要按「token 的最长合法前缀」处理，这是实现的主要复杂度；
- **性能**：每步掩码计算贵——用「状态 × token 集」的缓存表（编译一次，解码时查表），vLLM/llama.cpp 都做了增量优化；
- **不要过度约束**：文法只约束「格式」，语义留给模型——把内容规则也塞进文法会让模型无路可走（合法但空洞）。

## 二、执行反馈循环：语义正确性的引擎

语法对 ≠ 逻辑对。代码生成的语义保障靠**执行反馈**：

```
生成代码 → 跑单元测试/编译 → 失败则把报错回填上下文 → 重新生成 → 循环
```

三个升级形态：

1. **大规模采样 + 过滤**（AlphaCode）：同一题采样几十万份，按测试用例过滤 + 聚类去重——用算力换正确率（测试时算力的最早示范，见思维链深读）；
2. **Agent 式迭代修复**（SWE-bench 范式）：模型自己看报错栈、定位文件、改代码、重跑——把「调试」也交给 Agent（见 CUA 深读的同款循环）；
3. **过程奖励模型（PRM）**：给中间步骤打分而非只看最终结果——推理时按 PRM 引导搜索。

**评估**：HumanEval（函数级）/ SWE-bench（仓库级 issue 修复）/ LiveCodeBench（防污染，见评测基准深读）——仓库级的「真实通过率」长期在 50~70% 区间，是代码 Agent 的主战场。

## 三、仓库级上下文：产品的真正壁垒

补全/修改代码需要「跨文件意识」：函数定义在别的文件、类型在类型库里。上下文策略：

- **FIM（fill-in-the-middle）训练**：训练目标就是「给定前后文填中间」——补全产品的基础（见其专用主题的范式）；
- **检索式上下文**：按当前文件的 import/符号引用检索相关片段（树坐标签索/LSP 集成）——本质是代码版 RAG；
- **截断的艺术**：上下文装不下整个仓库——按依赖图的相关度排序，宁可截断注释也不截断类型定义。

## 四、要点总结

1. **约束解码的保证边界？** 格式 100% 合法（数学保证）；语义不保证——两层正交。
2. **文法如何变成掩码？** 文法→FSM（每状态=合法 token 集）→ 每步 logits 置 −∞ + 重归一；实现上按 token 前缀缓存。
3. **执行反馈为什么比「更强的模型」便宜？** 编译器/测试是免费的真值信号——把「猜对」变成「试对」。
4. **AlphaCode 的套路与代价？** 大规模采样+测试过滤；代价是百倍算力——测试时算力换正确率的极端版。
5. **仓库级补全的上下文难点？** 跨文件依赖、截断取舍、FIM 训练格式——壁垒在上下文工程不在模型。
6. **约束解码的性能优化？** FSM 编译缓存 + 增量掩码 + 跳表；大 schema 下仍是推理延迟的主要增量之一。
