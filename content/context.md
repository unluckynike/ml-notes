# 上下文工程深读：位置偏置的机制与压缩的纪律

这篇是**上下文工程**主题的深度补充。演示里的 U 形利用率曲线来自 **Lost in the Middle** 的实证发现，这篇讲清它的机制解释、压缩策略的取舍纪律，以及「上下文工程」作为一门工程学的完整清单。

> [!KEY] 一句话抓住本质
> 上下文不是「越大越好」的记忆条，而是**注意力资源有限的工作台**：位置有偏置（U 形）、内容互相稀释（干扰）、预算此消彼长。上下文工程 = 把这三条约束当成一等公民来设计输入——「什么进、什么序、占多少、多精确」。

---

## 一、U 形曲线的机制解释

Lost in the Middle（2023）的实验：把关键事实放在 20 个文档的不同位置，模型的召回率在**开头与结尾高、中间塌陷**——与人类阅读的首因/近因效应惊人相似。

机制解释（多个互补假说）：

1. **因果注意力的结构偏置**：开头 token 被「所有人看」（每个后续 token 的 attention 都覆盖它），结尾 token 离生成位置最近——中间 token 只被「路过」；
2. **训练数据分布**：文档/代码的重要信息天然聚集在首尾（标题/结论），模型学到了「中间不太重要」的先验；
3. **旋转位置编码的衰减**（RoPE 的远程衰减项）——远处 token 的注意力权重被系统性压低。

**工程含义**：检索内容的重排（最高分放开头、次高放结尾）、指令位置、关键约束的重复——都是零训练成本的结构优化。

## 二、压缩的纪律：有损但可控

长对话/长任务里，历史不能全量保留。三种压缩的取舍：

| 策略 | 做法 | 丢什么 | 风险 |
|---|---|---|---|
| **滚动摘要** | 旧轮次浓缩成一段 | 细节、语气 | 摘要漏掉后来变关键的信息 |
| **结构化状态** | 把对话抽成「事实/待办/约束」清单 | 叙述上下文 | 抽取遗漏（要模板化兜底） |
| **分层指针** | 窗口里放「索引+指针」，原文在库中按需取 | 即时性（多一次检索） | 检索失败则断链 |

**纪律**：压缩必须有**回归测试**——用固定任务集验证「压缩后的 Agent 还能不能完成任务」；摘要质量按「下游任务成功率」评估而非「摘要看起来全」（与 RAG 的评估分层同理）。

## 三、预算分配：任务决定配比

演示里的四种方案对应真实场景：

- **检索优先**（客服/文档问答）：60% 给检索内容——答案在资料里，示例多余；
- **示例优先**（格式敏感任务）：50% 给 few-shot——格式一致性 > 知识覆盖；
- **历史优先**（长期陪伴/多轮任务）：60% 给对话状态——连贯性是产品价值；
- **系统提示最小化**：约束写在系统层但**不重复**——重复指令会稀释而非强化（注意力是守恒的）。

**动态组装**（现代 Agent 框架的标配）：每次请求按「任务类型 × 当前状态」现场计算配比，而不是静态模板——这与「检索按需触发」（Self-RAG，见其深读）是同一思想在不同层的体现。

## 三·五、KV Cache 与上下文工程的交汇

上下文工程的「预算」在推理时有精确的物理对应——**KV cache 显存**（见推理优化深读的公式）。每一条进上下文的 token 都要占 cache：

$$\text{cache} = 2 \times L \times n_{kv} \times d_h \times \text{len} \times \text{bytes}$$

这给了「上下文纪律」一个硬约束：128K 窗口 × fp16 × Llama-7B ≈ 60GB——**塞满窗口在物理上不可行**。工程对策按层：

- 压缩历史 = 减少 cache 长度（省显存与注意力计算双重收益）；
- 结构化状态替代流水账 = 同样信息量更少 token；
- MQA/GQA = 同样长度下 cache 缩数倍（架构层）；
- 滑动窗口/淘汰 = cache 有上限（StreamingLLM 思路：保留 attention sink 的开头几个 token + 最近窗口，长对话不崩）。

「上下文工程」因此有了两层含义：提示层的信息管理（本主题）与 KV 层的物理管理（推理优化主题）——Agent 系统的长期记忆设计必须同时考虑两者。

## 四、面试要点速答

1. **Lost in the Middle 说明什么？** 位置利用率 U 形（首尾高中间低）；重排检索内容是零成本优化。
2. **三种压缩的取舍？** 滚动摘要（有损）/结构化状态（抽取风险）/分层指针（多一次检索）——都必须配回归测试。
3. **为什么重复指令不是强化？** 注意力守恒：重复占用预算且稀释其他关键内容；约束要精不在多。
4. **上下文工程与提示工程的分界？** 提示工程管「内容怎么写」，上下文工程管「窗口的空间管理学」——什么进、什么序、占多少。
5. **长任务 Agent 的上下文设计？** 结构化状态 + 分层指针 + 任务级回归测试——三件套缺一不可。
6. **利用率曲线会变吗？** 随模型/训练/窗口长度变——结论要按模型实测，不能跨模型照抄。
